## 2. Linter path chosen: Oxlint (why)

SETUP.md says "If neither [ESLint nor Oxlint] is present, set up Oxlint." That is exactly this project's situation — the only incumbent linter is **Biome**, which the ESLint/Oxlint setup paths do not touch. Rationale for Oxlint over ESLint:

- **Follows the explicit spec instruction** for the "neither present" branch.
- **Oxlint is the lighter, native-binary tool**, consistent with the project's existing native tooling (Biome is also a native binary). The ESLint path would pull in the full ESLint `@eslint/*` JavaScript toolchain and a second JS-based linter for no benefit here.
- **No peer-dependency issue.** `@shadcn/lint@0.1.0` declares `eslint >=9.30.0` as an *optional* peer (`peerDependenciesMeta.eslint.optional: true`, verified against the npm registry), so bun installs it cleanly with no peer warnings regardless of host.
- `jsPlugins` is `@shadcn/lint`'s documented first-class registration for Oxlint (README "Get started"), and the plugin's own rule set is what the project will rely on; the general correctness job stays with Biome.

Trade-off noted: Oxlint's JS plugin API is currently in **alpha** (per the README and Oxc docs). If it proves unstable in practice, the documented ESLint fallback is a small config change; see caveats below.

## 5. Where to add rules later, and caveats

Add rules by editing `.oxlintrc.json`'s `rules` object, e.g.:

```json
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "jsPlugins": ["@shadcn/lint"],
  "categories": { /* …remain off… */ },
  "rules": {
    "shadcn/no-restyle": ["error", { "allow": ["layout"] }]
  }
}
```

Reference material:

- Available rules: https://github.com/shadcn-ui/lint/blob/main/README.md#rules
- Rule options: https://github.com/shadcn-ui/lint/blob/main/docs/rules.md
- Design-system configuration (variants, contracts, messages): https://github.com/shadcn-ui/lint/blob/main/docs/design-systems.md

Caveats:

- **Oxlint JS plugin API is alpha** (also not subject to semver). If issues appear, switch to the ESLint path: `bun add -D eslint @typescript-eslint/parser`, an `eslint.config.mjs` with `import { plugin as shadcn } from "@shadcn/lint"`, `plugins: { shadcn }`, no rules — but note that would introduce a second JS linter alongside Biome.
- **`@shadcn/lint` bundles `@typescript-eslint/parser`** as a dependency, so the TS/TSX parsing used by the plugin (no type info) is already present and was verified producing findings on `.tsx` files during testing.
- **Coexistence with Biome:** Biome (`bun run check`) is the general linter+formatter; Oxlint (`bun run lint`) is reserved for `@shadcn/lint` design-system rules, with Oxlint's built-ins disabled to avoid duplication. When rules are later enabled, disable them inside the component directory (`src/components/ui/**`) if components should be allowed to style themselves (per the README's override guidance).
